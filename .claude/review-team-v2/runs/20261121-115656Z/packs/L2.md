- P1 A range the person picks (range button incl. the one already shown, or Custom Apply) before the setting is read is kept. holds: state.rangePicked set in ranges click handler before the same-range early return, and in applyDates; firstLoad checks !state.rangePicked.
- P2 A load that started without the setting (background usage.changed) is redone on the default. holds: moved=true → load(); load() while busy sets state.again → reload after the first finishes (panel.js load finally).

# Method

## Every lens

- Read the code, then the claim. Open each changed file at the target and read the function around every hunk (the function, not the file), plus the callers and callees the hunk depends on. A diff alone hides the guard three lines above it and the consumer two files away.
- Follow real values. When the code calls something, read the callee with the arguments this call site actually passes, including every argument it omits and the default that fills it.
- A candidate needs a trigger you can write down as numbered steps: who does what, in what order, with what input, in which environment. If you cannot write the steps, keep reading until you can or drop it.
- Report what the change makes wrong (introduced) or newly reachable (exposed). A defect that behaves the same on the baseline is `pre-existing`: report it, labelled.
- Name the **class** of each candidate and **sweep** for it: list the other places the same pattern occurs (sibling functions, other platforms, other variants, other reset or entry paths) and say which you checked. One instance usually has siblings, and a fix that closes one instance leaves the rest.
- Things you suspected and ruled out are results too. Record them with the `path:line` of the guard that rules them out.

## state

Method: inventory every piece of state the change adds, reads, or writes, then run every event against it.

Artifact, part 1, the inventory: `state | every copy (memory, disk, local storage, server, other tab, other process, cache) | writers | readers | clear and reset paths | authoritative copy | scope (tab, session, account, device, install) | lifetime (until reload, restart, logout, upgrade)`.

Artifact, part 2, the event cross: for each state row, what happens on: startup and restore, reload, logout and account switch, mode or policy change, "reset all", upgrade from old data, a failed or offline write, a response that arrives late, and the same action taken in a second tab, window, or process.

- Every copy must be written, cleared, and migrated together. For each clear path, count the copies it clears against the copies that exist.
- When the change adds an item to a family (another setting, another key, another mirrored field), find the code that already handles the rest of the family (reset, export, sync, pending-write, migration) and confirm the new item was added to each.
- State that comes with a partner (a mode and the flag that qualifies it, an id and its generation) must be persisted, restored, and cleared with its partner.
- Establish scope from the code that keys the storage (the path builder, the table key, the tenant column), then check it matches: a guard that checks this tab's value cannot protect state that is shared by the install or the account.
- Order at startup: what is restored before the authoritative answer arrives, and what happens when the authority then disagrees? Clearing storage is different from clearing the in-memory copy.
- A record written to mean "already done" must be written after the thing succeeded, on eligible paths only.
- Links between records must use a stable identity. "The latest row", a position, or an id the store can reuse will attach the link to the wrong record after an insert or delete.
- After one of several operations fails, check what the cache now claims and whether later cleanup trusts that claim.
- Migration: remove the old thing only after the new one is live, and detect existing users by evidence that survives every older version.

Classes:
- A mode restored at startup while its companion flag starts false, so the protection the flag provided is gone after a restart.
- A reset clears the browser copy; hydration then reads the server copy back and the cleared setting returns.
- A clear that runs only while this tab holds the setting, when another browser can save it to the shared store.
- A stale GET resolving after a newer local choice and overwriting it, because the choice did not bump the version the merge checks.
- State restored from storage before the auth status that forbids it arrives; the later clear wipes storage and leaves memory set.
- A pending-write queue the flush ignores, so a reset queued before hydration is lost when the page reloads.
- A hotkey cache set to "nothing registered" after one binding failed while the others stayed grabbed, so the release step skips them.
- An upload link attached to "the newest history row"; deleting that row lets the next insert reuse its id and take the link.
- The legacy login item unregistered before the new agent is confirmed enabled, leaving the user with neither.

## time

Method: find every point where the code waits or hands work off, and ask what changed in the meantime.

Artifact: one row per suspension point (await, spawn, callback, timer, debounce, lock acquisition, queue, external process, network call): `captured before | used after | who can change it in between | guard that detects the change`.

- Staleness: the older operation finishes after a newer one started. Its result or its error must apply only to its own generation. Look for the identity, version, or generation check; equality of contents is a weak identity.
- Ownership: the session, window, or object that started the work is closed or replaced while the work is queued or running. Where does the result land?
- The user keeps going: for each pending phase, try every input the UI still accepts (Enter, Escape, another edit, close, the same command again). A result must not be dropped, and newer edits must not be discarded by a completion that captured an older revision.
- Check, then act: a validity check made before taking the lock, or before an await, can be false by the time it is used.
- Two at once: two instances, processes, tabs, or tests sharing a temp path, a file name, a port, a global, or a registry. Uniqueness needs a component that differs per instance.
- Late events on recycled identity: an event for an old item arriving after its id, path, or slot was reused.
- Teardown races: a write in flight when the page reloads, the window closes, or the process exits; an error swallowed just before the reload.
- For each lock: what it covers, what reads or writes the same data outside it, and the order locks are taken.

Classes:
- A rejection from an older shortcut-binding request arriving after a newer registration and marking the newer bindings failed.
- A new selection starting an OCR read while the previous read is still running, with no cancellation of the old one; workers queued for a session that already closed.
- Enter pressed while the result is still being computed closes the session and drops the result.
- "Save, then close" closing after any successful write, even though edits arrived while the save ran.
- A currency check made before the registration lock, so a same-key remap marks a live binding failed.
- Two instances printing the same format sharing one temp file path.
- A delayed "shortened" event writing an old short URL onto a row whose id was reused.

## ripple

Method: start from what changed and walk outward to everything that depends on it and everything that should have changed with it.

Artifact: one row per changed symbol, contract, stored format, constant, and config key: `what changed | every consumer (path:line) | consumer still correct? | siblings that need the same change | done?`. Start from "Unchanged code that still uses changed names" and "Same-named files the change did not touch" in `brief.md`, then search for the consumers a name search misses: re-exports, string keys, registrations, reflection, serialized field names, callbacks, tests and their stubs.

- Callers: read each one. Group callers only after confirming they pass the same arguments and expect the same errors.
- Readers of changed data: every reader of a field, record, file, status, or event whose meaning or timing changed, including clients that store it and send it back.
- Siblings: the same fix or feature on the other platforms, the other entry points (CLI, UI, API, hotkey, tool call), the other request kinds, the other reset scopes, the other models or providers. When a sibling was left alone, decide whether that is correct.
- New dimension: when the change adds a second kind of something (a price tier beside the base rate, a custom item beside catalog items, a second adapter or provider, another tool or mark kind), list every function that handled the first kind and read what each does with the second. A function the change did not touch is the likely miss.
- Sources: a consumer reading status or options from a neighbouring component's state instead of its own.
- Removed and renamed names: every remaining reference.
- Pairs that travel together: schema and migration, flag and docs, producer and parser, manifest and lockfile, import graph and test stubs, feature and its off-switch.

Classes:
- A fix applied to "Reset all" while the page-level reset with the same gap stayed broken.
- Six command-line tool actions ignoring their file argument after five were fixed.
- A music route fixed for a named model while speech, clone, edit, and convert routes failed the same way with no model named.
- A tool's option check reading another model's status, so the options were never validated.
- A new import from a module the existing test stubs do not provide, breaking nine unrelated tests.
- Tiered rates added to the cost calculation while the savings figure and the price-sync diff beside it still read base rates only.
- A session marker one transcript adapter emits and the adapter for the other agent never does, so the accounting downstream differs by agent.
- An install plan that tracks catalog ids only, so a selected custom model whose file is gone counts as complete and the fallback engine is skipped.

# Domain checks

## persistence

- Write, reload, and read back: types that change on the round trip, missing and extra fields, defaults applied on load.
- Old data: records written by each earlier version, read by the new code. New data read by old code if downgrade or mixed versions are possible.
- Migration order and re-entry: interrupted halfway, run twice, run on already-migrated data.
- Partial writes and transactions: what is durable if the process dies between two writes.
- Deletion and id reuse; foreign references to rows that can disappear.
- Every mirror of the stored value (cache, client copy, server copy) and what invalidates each.
- Reset, export, import, and sync paths must include every new key.
