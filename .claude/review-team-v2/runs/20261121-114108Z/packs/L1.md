# Ownership model — PR #7 fix delta (cf7b7cf)

Prior run: F-001 (default not followed while open, panel.js clearFilter) and F-002 (gate on report/busy as proxy for user pick, firstLoad). This delta is the fix.

## 1. Promise
- P1 A range the person picks (range button incl. the one already shown, or Custom Apply) before the setting is read is kept. holds: state.rangePicked set in ranges click handler before the same-range early return, and in applyDates; firstLoad checks !state.rangePicked.
- P2 A load that started without the setting (background usage.changed) is redone on the default. holds: moved=true → load(); load() while busy sets state.again → reload after the first finishes (panel.js load finally).
- P3 A failed picked load is retried on the picked range, not the default. holds: rangePicked keeps range; !report && !busy → load().
- P4 Changing the setting while open updates state.defaultRange (used when a custom range is cleared); it does not switch the shown range. holds: host.settings.onDidChange → readDefaultRange.
- P5 Unknown/unreadable → keep 7d. holds: readDefaultRange returns null.

## 2. State
| State | Lives | Writer | Reader | Cleared |
|---|---|---|---|---|
| state.rangePicked | panel memory | ranges click, applyDates | firstLoad | never (only matters before first read) |
| state.defaultRange | panel memory | firstLoad, onDidChange callback | clearFilter | — |
| state.again | panel memory | load() when busy | load() finally | load finally |

## 3. Scenarios
- usage.changed during pending get: onChanged → load (7d, busy) → get resolves 30d → state.range=30d, moved → load() → busy → state.again → after 7d finishes, load(again) with 30d. Test covers (calls 7d,30d).
- Settings change while open: onDidChange({key}) → readDefaultRange → state.defaultRange; later clearFilter('range') → that value. Test covers.

## 4. Decisions
- firstLoad: (range valid) × (rangePicked) × (range==current) × (busy/report) — moved only when valid, not picked, different.

## 5. Boundaries

- settings.get deadlined by the shell (plugin-panel-shell.js:115).

# Method

## Every lens

- Read the code, then the claim. Open each changed file at the target and read the function around every hunk (the function, not the file), plus the callers and callees the hunk depends on. A diff alone hides the guard three lines above it and the consumer two files away.
- Follow real values. When the code calls something, read the callee with the arguments this call site actually passes, including every argument it omits and the default that fills it.
- A candidate needs a trigger you can write down as numbered steps: who does what, in what order, with what input, in which environment. If you cannot write the steps, keep reading until you can or drop it.
- Report what the change makes wrong (introduced) or newly reachable (exposed). A defect that behaves the same on the baseline is `pre-existing`: report it, labelled.
- Name the **class** of each candidate and **sweep** for it: list the other places the same pattern occurs (sibling functions, other platforms, other variants, other reset or entry paths) and say which you checked. One instance usually has siblings, and a fix that closes one instance leaves the rest.
- Things you suspected and ruled out are results too. Record them with the `path:line` of the guard that rules them out.

## trace

Method: walk every hunk line by line and state, for each, what the old code guaranteed and what the new code does instead.

Artifact: one row per hunk: `hunk | old behavior | new behavior | inputs where they differ | intended?`.

- For each difference, decide whether the author meant it. An unintended difference is a candidate.
- At every call in changed code, check each argument against the callee's parameter list. An omitted argument takes a default; read what that default makes the callee do, all the way down through nested helpers.
- For every fallible call, follow the failure: is the error returned, logged, swallowed, or turned into a success message? What does the user see?
- For every early return, break, and `?`: what cleanup, unlock, release, or state update below it is now skipped?
- Check units and reference frames on every value: point versus box, top-left versus centre, pixels versus logical units, bytes versus characters, inclusive versus exclusive bounds, index versus count, old coordinate space versus new after a transform.
- Check text assumptions: separators inferred from position, ASCII-only handling, case, locale, scripts written without spaces.

Classes:
- A transform applied to an anchor point when the object has an extent, so the object shifts by its own size (rotating a bitmap's top-left corner instead of its box).
- An inner call that omits an argument; the default sends a nested helper down a path that resets the state the outer function just set up.
- A failed operation reported to the user as done (a copy that failed shows "copied").
- A separator or space synthesized between items because they are separate boxes, which is wrong for text that has none.

## cases

Method: for every decision the change adds or edits, write the complete case table, including the cases the code never names.

Artifact: one table per decision: every combination of input variant, outcome, and environment, with the branch that handles it. A row with no branch, or handled by a fallthrough, is a candidate.

- Variants: list every member of each enum, union, request type, event kind, or flag set that reaches the decision, then find the arm for each. Include "two flags at once", "flag repeated", "none given", and "name omitted".
- Third-party values: for a library, OS, runtime, or protocol the code consumes, open its source or docs at the pinned version and list what it can actually return or emit, on every version the project says it supports. Handle each. Coalescing, batching, and debouncing layers produce combined events the raw API never shows.
- Outcomes: success, failure, partial success, unsupported, pending, needs-user-approval, timeout, cancelled. Follow each to its effect. A marker, flag, cache entry, or "done" record must be written only on the outcome it describes.
- Environments: operating systems, build profile (debug, release), install mode (installed, portable, sandboxed, unbundled), read-only or missing storage, permissions denied, first run versus existing user versus upgrading from each older version.
- Absence: anything that iterates over what exists is blind to what was removed. Where the code diffs, counts, resets, or restores, ask what happens to an item that is gone.
- Defaults: when a field is left unset and inferred later, check that the inferred path is the safe, bounded one and matches what an explicit setting would have chosen.
- Twin gates: when two places decide the same question (a validator and a consumer, two allowlists, two thresholds, two predicates on the same file type), they must agree on every input. Find an input one accepts and the other rejects.
- Writer and reader: for everything the change writes (a settings entry, an overlay row, a cache record, a message), list each shape the writer can emit, including the partial one a user gets by choosing some of the rows, and feed each to the code that later loads it. A write that reports success must load.
- Shared key space: where reserved names and names taken from user data key the same map, find the user value that equals a reserved one.
- Precedence: first wins or last wins, and does that match the documented or reference behavior?
- Classification by equality on a value that has a fallback (a path that falls back to the default directory) misclassifies the fallback case.

Classes:
- A request variant added in the same change is handled in one branch and forgotten in the rewrite step next to it (file uploads rewritten, URL uploads not).
- A rename inside a watched folder arrives as one combined "both" event from the debouncer, matching neither the "arrived" nor the "left" predicate, so the file is skipped silently.
- A first-run marker written even when enabling failed, when the platform reported unsupported, on a read-only portable copy, and in debug builds, so the default is never retried or leaks into shared state.
- "No settings file" treated as a new install, re-enabling a default for existing users who had opted out in an older version.
- A custom item passes the add-time validator but the consumer only accepts catalog ids.
- Applying one rate row of a model the catalog lacks writes an entry the catalog builder rejects for its missing rates, while Apply reports success and the model stays unpriced.
- A grouping label such as `(commands)` keyed in the same map as real folder names, so a folder with that name merges into the group.
- A truncated compressed file accepted at end of input on one supported runtime version, then cached as fully read, so its tail is never read again.
- A codec left unset is inferred from the extension and takes the single-pass path that buffers every frame; only an explicit codec took the bounded two-pass path.
- "Reset all" counts and restores only rows that still exist, so a removed built-in item cannot be brought back.
- A repeated command-line flag overwrites; the reference implementation honors the first.

## journey

Method: be the user. List every way a person or a calling program reaches the changed behavior, then walk each path one action at a time through the real handlers, carrying the actual value of every field.

Artifact: one table per flow: `step (what the user does) | handler (path:line) | value of each field and flag after the step | what the user sees`, closed by one row: `what the flow leaves stored or shown | the code that uses it next (path:line) | does that code work with exactly this value`. A flow without its closing row is unfinished: a handler that looks right on its own is half of the answer.

- Start states: first use with nothing saved, every input left blank, each preset and default exactly as shipped, and an existing user's saved values.
- Blank: follow each empty input into its handler and then into the next thing the user does. Decide what blank means at each (not set, use the default, or a real value); two steps that read it differently are a candidate, and so is a state the user cannot get out of.
- Switches: change option A to B, then back. For each field A filled, read what B's handler does with it. A value left over from A is what B's next action uses.
- Option cross: when the change offers a choice (color, size, tool, model, mode), cross every choice with every kind of thing it applies to, and check each pair gives something usable: visible, legible, valid.
- Every ending of an action: done, cancelled midway, failed and retried, repeated, undone, and ended where it began (a drag released at its start, a dialog confirmed with no edits). A flag raised when the action starts must be lowered on each ending.
- Dead ends: a state where the feature needs a value the interface gives no way to supply, or a control that does nothing and says nothing.

Classes:
- A preset that ships with a blank model field: the connection test treats blank as a known model and offers no choices, and the request path rejects a blank model, so the feature cannot work until the user guesses a name.
- Switching from a preset with a model to one that expects the server's model leaves the old name in the field, and the test filters the server's list by that stale name.
- A color swatch that sets a shape's fill while its numeral stays white: the white swatch gives white on white.
- A resize released at its starting rectangle sends no update, so the "resized" flag raised at the start is never consumed and the next plain move is treated as a resize.

# Domain checks

## persistence

- Write, reload, and read back: types that change on the round trip, missing and extra fields, defaults applied on load.
- Old data: records written by each earlier version, read by the new code. New data read by old code if downgrade or mixed versions are possible.
- Migration order and re-entry: interrupted halfway, run twice, run on already-migrated data.
- Partial writes and transactions: what is durable if the process dies between two writes.
- Deletion and id reuse; foreign references to rows that can disappear.
- Every mirror of the stored value (cache, client copy, server copy) and what invalidates each.
- Reset, export, import, and sync paths must include every new key.
